# Improvement Changelog — Cloud Triage Agent

This traces the solution from a simple baseline through every meaningful
change to the final result, using the same evaluation cases and scoring
method (correct incident type + severity, out of 10) at every stage so the
numbers are directly comparable.

| Stage           | What I tried and why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Evidence                                                                                             | Decision / Learning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Baseline**    | Started with a simple rule-based approach: keyword/substring matching against the incident description (e.g. "cpu" → performance, "s3" + "public" → security), no AI involved. Established the starting point before adding any intelligence.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Baseline 5/10 (50%)                                                                                  | Established the starting point. A fixed keyword list is fragile — symptoms split across multiple weak signals (e.g. "429 errors" + "concurrent executions at limit") don't map to any single keyword rule.                                                                                                                                                                                                                                                                                                                                                                                     |
| **Iteration 1** | Added a rule-based agent: classify → retrieve (knowledge-base similarity search) → verify → summarize, still no LLM. Hypothesis: even without AI, grounding a guess against known incident patterns should catch mistakes a flat keyword match misses.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Agent 7/10 (70%)                                                                                     | **Kept the shape, flagged a real limitation.** The agent beat baseline by 2 cases, but produced one regression: the classifier tied on two categories from a single ambiguous keyword ("Lambda" pulling toward "throttling" on a cost-anomaly case) and picked the wrong one — and the verify step could only *lower confidence*, never *change the answer*, so a correctly-retrieved KB entry was discarded instead of used. This became the specific target for the next iteration: a verifier needs the authority to overturn a bad initial guess, not just comment on it.                  |
| **Iteration 2** | Replaced both classify and verify steps with real LLM calls (kept the same classify → retrieve → verify shape), explicitly instructing the verify step that it *may override* the initial classification when retrieved evidence disagrees — directly targeting Iteration 1's regression. First attempt used Amazon Bedrock; hit a sequence of account-level provisioning walls (a model-specific use-case approval gate, then a newer model unavailable for the account, then a token-per-day quota exhausted almost immediately, then most Bedrock quotas simply not provisioned for the account at all — confirmed by testing a second, unrelated model on Bedrock and hitting the identical wall).                                                                                                                                                                | No successful run obtained on Bedrock                                                                | **Removed.** Switched providers entirely to Google Gemini rather than wait on AWS account provisioning. This cost almost no code: the LLM client was already isolated behind a single interface, so only that one file changed — the actual agent logic (classify/retrieve/verify, the override permission) didn't change at all. Lesson: don't treat a single LLM provider as a single point of failure if the project's core value depends on a call to it succeeding.                                                                                                                       |
| **Iteration 3** | Got Gemini working, but the first *complete* real run scored the agent **below its own baseline** (agent 50% vs. baseline 60%) — a genuine regression, not an infra failure. Diagnosis, confirmed by a captured execution trace: on the one case where the agent did worse, retrieval found no matching knowledge-base entry, so the verify step had *no evidence to check against* — and it still changed the answer anyway, escalating severity upward with nothing grounding that change. Fix: added an explicit severity rubric (concrete criteria for low/medium/high/critical, with an instruction not to escalate severity just because more context is available to cite) and added canonical `incident_type`/`typical_severity` labels to every knowledge-base entry, so verification has a concrete fact to anchor to instead of re-reasoning from scratch. | Baseline 8/10 (80%), Agent 10/10 (100%)                                                              | **Kept — this is the main contribution.** A verification step's value is entirely contingent on having something worth verifying against; the fix wasn't removing its authority to change an answer (that reintroduces Iteration 1's bug), it was making that authority conditional on real grounding. Confirmed via captured execution traces, not just the aggregate score: on two separate cases, the model's own first-pass guess made the *same* mistake as the baseline, and the verify step corrected it by citing the knowledge base's canonical label for that exact failure pattern. |
| **Final**       | Combined everything that worked: Gemini-backed classify → retrieve → verify, verification with conditional override authority, severity rubric, KB canonical grounding — kept alongside the original rule-based version (still available via a zero-cost, no-API-key evaluation path) as a fast sanity check and a clear before/after reference point.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Baseline 8/10 (80%), Agent 10/10 (100%), rule-based baseline 5/10 (50%), rule-based agent 7/10 (70%) | **Identified the main contribution:** grounding verification in curated, canonical reference data — not a bigger model or a longer prompt — is what took the agent from a regression below its own baseline to a clean win over it. Every stage above was decided by re-running the identical 10-case evaluation, not by inspection or intuition.                                                                                                                                                                                                                                              |

## The one open, unresolved observation

One case (EC2 CPU Spike) flipped from incorrect to correct for the agent
across two runs of *identical* code — no further prompt change explains
it. This is called out rather than quietly adopted as a win: it's most
likely ordinary LLM sampling variance, and it means that specific case's
fix isn't yet a guaranteed, reproducible behavior, even though the
mechanism behind it (KB-grounded severity correction) is independently
confirmed on a different case via a captured execution trace.
